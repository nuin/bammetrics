# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

bammetrics reimplements Picard BAM QC metrics in Rust (on `noodles` 0.119) and exposes them to Python through PyO3 and maturin. The goal is output identical to Picard 3.5.0, field for field and string for string. Implemented: `CollectInsertSizeMetrics`, `CollectAlignmentSummaryMetrics` and `CollectGcBiasMetrics` (all four accumulation levels), `CollectQualityYieldMetrics`, `QualityScoreDistribution`, `MeanQualityByCycle`, `CollectBaseDistributionByCycle`, `CollectDuplicateMetrics`, `AccumulateQualityYieldMetrics`, `EstimateLibraryComplexity`, `CollectMultipleMetrics` (those seven programs and `CollectSequencingArtifactMetrics`, eight on one read; the artifact program takes the prefix itself), `CollectHsMetrics` and `CollectTargetedPcrMetrics` (all four levels, `PER_TARGET_COVERAGE`, `PER_BASE_COVERAGE`, `THEORETICAL_SENSITIVITY_OUTPUT`), `CollectWgsMetrics`, `CollectRawWgsMetrics`, `CollectWgsMetricsWithNonZeroCoverage`, `BedToIntervalList`, `CollectRnaSeqMetrics` (all four levels, `RIBOSOMAL_INTERVALS`, the normalized coverage histogram), `CollectVariantCallingMetrics` (VCF input, `DBSNP`, `TARGET_INTERVALS`, `GVCF_INPUT`), `AccumulateVariantCallingMetrics`, `GenotypeConcordance` (every option but `OUTPUT_VCF`), `CompareMetrics` (every option, Picard's exit code), `CollectOxoGMetrics` (every option; `CONTEXT_SIZE` at most 4 without `CONTEXTS`), `MarkDuplicates` (writes the marked BAM; every option but the flow-based ones), `CollectSequencingArtifactMetrics` (the five files, every option, also a `CollectMultipleMetrics` program) and `ConvertSequencingArtifactToOxoG`. `CreateSequenceDictionary` writes the `.dict` of a plain, gzip or bgzip FASTA. `CollectJumpingLibraryMetrics` (several `INPUT`s, every option) is implemented. `BamIndexStats` prints Picard's index statistics from the `.bai` or `.csi`. `CheckDuplicateMarking` checks that every record of a queryname carries the same duplicate flag (`MODE`, `OUTPUT`, Picard's log lines and exit code). `FifoBuffer` copies standard input to standard output through a memory buffer (`BUFFER_SIZE`, `IO_SIZE`, `DEBUG_FREQUENCY`, `NAME`; no `INPUT`, no `OUTPUT`; Picard's log lines; the Python function raises `UsageError`). `ViewSam` prints the header and the records of a SAM, BAM or CRAM as SAM text, as htsjdk writes it (every option; standard output as it is read; the verb `view-sam` takes `-o`). Every tool that reads a BAM also reads SAM text (plain, bgzip or gzip, told by its first bytes, checked as htsjdk checks it at `VALIDATION_STRINGENCY`; `crates/core/src/sam_text.rs`) and a CRAM (3.0, 3.1) with `R=`. Two checks with no Picard counterpart (`docs/06_clinical_checks.md`): `CollectCoverageGaps` (class `bammetrics.qc.CoverageGapMetrics`, the target bases under `MIN_DEPTH` as maximal runs with the Hs per-base depth, plus a `GAPS_FILE` BED) and `CollectSexCheckMetrics` (class `bammetrics.qc.SexCheckMetrics`, reads per base on X, Y and the autosomes against `EXPECTED_SEX`). `bammetrics chain BAM + STEP [+ STEP ...]` (`docs/chaining.md`) runs several steps on one BAM in one process, records handed on in memory: `mark-duplicates` as a transform, the 13 one-pass tools as taps, `write` for the BAM, from the command line, a TOML plan file or Python (`bammetrics.chain`, `bammetrics.step`). The registry (`TOOLS`) holds 33 tools at 0.22.0, 34 with `ViewSam` (wave W05 part A) and 35 with `SortSam` (wave W05 part B: also the sort step of a chain under `--sort-memory`, any number of transforms in one chain through a spool, the planner and its free-space refusal; unreleased). `ROADMAP.md` holds the product plan, `KNOWN_DIFFERENCES.md` lists where output differs on purpose.

## Commands

```bash
cargo build --release                       # target/release/bammetrics
cargo test --workspace                      # unit and integration tests
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check

# Picard concordance (needs picard 3.5.0, samtools, bwa, uv on PATH)
make concordance                            # corpus, Picard references, golden suite, pytest tests/concordance
make golden                                 # crates/cli/tests/golden.rs against tests/golden (byte for byte)
.venv/bin/python tests/data/make_markdup_bam.py   # rewrite tests/data/markdup.bam, the MarkDuplicates fixture (pysam)
make golden-update                          # rewrite tests/golden after an intended CLI change
make python-test                            # maturin develop into .venv, pytest tests/python
make wheel-check                            # maturin build, fresh venv, mypy on the stub, import, stub vs dir(bammetrics)
make fuzz SEED=1 N=200                      # tests/concordance/fuzz.py: random BAMs through both tools
make bench-wgs                              # T4 scale run of the coverage tools (benches/wgs_bench.py)
cargo test -p bammetrics-cli --test chain   # chained equals staged (docs/chaining.md); the t1 and foundation cases need tests/corpus/out
make picard-fields                          # crates/core/picard_fields.tsv from picard.jar (CompareMetrics types)
MULTIQC=path cargo test -p bammetrics-cli --test formats multiqc   # MultiQC reads PREFIX.verdict_mqc.json (skipped without multiqc)
make budgets                                # docs/05 4.8 size and speed budgets (crates/cli/tests/budgets.rs: report and formats growth), fails at 2x a target
make a11y                                   # axe-core, reflow and Tab check of the report pages (benches/a11y.mjs; needs node and npm)
UPDATE_DOCS=1 cargo test -p bammetrics-verdict --test doc_presets   # rewrite the preset tables of docs/verdict.md
make harness-test                           # pytest tests/harness: the Picard queue, compare_bam, compare_vcf, spec_agent on stand-in tools (no JVM)
make deny                                   # cargo deny check against deny.toml (cargo install cargo-deny --locked; not in CI)
make deflater-spike                         # benches/deflater_spike.py: Picard's BGZF blocks against three deflaters (docs/concordance.md, BAM bytes)
python3 tools/spec_agent.py SortSam         # the option table of `picard SortSam --help` as a starting spec (--markdown for a table)
python3 tests/concordance/picard_lock.py --status   # who holds the Picard queue

# Python module
python3 -m venv .venv && .venv/bin/pip install maturin pytest pysam
.venv/bin/maturin develop --release

# One tool, Picard syntax (KEY=VALUE, or --KEY VALUE as Picard 3 takes it)
target/release/bammetrics CollectInsertSizeMetrics I=in.bam O=out.txt METRIC_ACCUMULATION_LEVEL=SAMPLE

# Several steps in one process (docs/chaining.md); --dry-run prints the plan
target/release/bammetrics chain in.bam -o out/s + mark-duplicates + insert-size + write --index
```

`picard` is a wrapper script around Homebrew openjdk. Plain `java` on PATH may be broken; call `picard`. CollectInsertSizeMetrics, and the three by-cycle tools when given `CHART`, need an `Rscript` on PATH; `tests/concordance/run_picard.py` puts a no-op one in `target/fakeR`, so no PDF is written.

## Layout

Cargo workspace (root `Cargo.toml`, one `Cargo.lock`):

- `crates/core` (`bammetrics-core`): the metrics library.
- `crates/cli` (`bammetrics-cli`): a library and the `bammetrics` binary. `src/lib.rs` holds every verb module, `Cli` and `run` (the dispatch of docs/05 section 2.1, Picard class first, then the grammar verbs, `chain` among them and `plan` when its arguments describe a chain, then the clap verbs `report`, `check`, `qc`, `plan` and `convert`); `src/main.rs` only calls `bammetrics_cli::main`, so the Python module runs the same code. The verb grammar of phase 8: `grammar.rs` (`Flag`, `parse`: kebab, `--PICARD_KEY`, `KEY=`, one-letter shorts with attached values, the boolean forms, did-you-mean), `verbs.rs` (`VERBS`, one `Verb` per registry tool with its output naming; `Verb::flags` builds the flags from the tool's option table plus the shared options; `Verb::run`), `collect.rs` (the `collect` verb), `info.rs` (`tools`, `presets`, `help`, `completions`, the clap command that lists every verb), `format.rs` (`--format` over `crates/formats`: `parse_list` for `picard,json`, `sibling` for the `FILE.json` a further format is written to, `render_all` with one set of header lines, `summary` from a `Verdict` to the formats crate's `VerdictSummary`), `convert.rs` (the `convert` verb: Picard text or JSON in, any format out, `-` for stdin and stdout, `--table`). The `chain` verb of W04 (docs/chaining.md), `chain.rs` and `chain/`: `chain.rs` (`Spec` and `StepSpec`, a chain as asked for; `run`, `run_plan`, `is_chain`, which tells a chain's `plan` arguments by a `+` or `--plan`), `chain/args.rs` (the command line: the chain's options and the source before the first `+`, one step per `+`; `global_flags`, `write_flags`, `step_flags(verb)`, `help`, `step_help`; `chain_option_on_step`, the `belongs to the chain` error for a chain option after the first `+`; `not_a_step`, the refusal of a verb that cannot be a step, with its own reason for `fifo-buffer`: a chain has no pipe to buffer), `chain/planfile.rs` (`--plan FILE`: one `[chain]` table and one `[[step]]` per step through `bammetrics_core::toml`, every key checked against the verb's flags with its line and the closest name, an option given twice under two spellings refused; `read` records the file in `Spec::plan_file`, and a file that is not UTF-8 text is a usage error), `chain/prepare.rs` (`prepare`: a `Spec` into a `Chain` of `Planned` steps; each step parsed by its own `Verb::flags` and checked as its verb checks it, `Role::Transform`, `Tap` or `Write`, the stream it reads (`in`, `marked`, `--as`), names under the prefix from `file_extensions`, the Picard command line in `qc`'s order, an empty prefix or file name refused; every usage error before the first read, as `step N (verb): ...`), `chain/claims.rs` (`stage::Outputs` for two steps on one file; `inputs_of`, the files the chain reads by device and inode: the source, the reference and its `.fai`, each step's input files and the plan file; `refuse_overwriting_inputs`; `check_one_stdout`), `chain/describe.rs` (`plan_text`: segments, one `barrier` line per transform, the files of each step, the temporary and output disk, the peak memory), `chain/planner.rs` (the planner of docs/07 2.4: `estimate` per barrier from constants measured on 8.4 M exome records, `needs` per file system, `check_space`, the free-space refusal before the first read unless `--force-space`; `parse_bytes` for `--sort-memory`), `chain/run.rs` (`execute`: `stage::run_chain`, every file written through `format::render_all` and `registry::write_to`, an `Outcome` with one `StepOutcome` per step: `StepStatus`, files, a transform's counters; `summary`, the lines on standard error; `sample_name`), `chain/python.rs` (the Python face: `chain_keywords` from `global_flags`, `step_table(name)` with a step's `Keyword`s from `registry::python_keywords` matched to `step_flags(verb)` plus `panel` on `hs_metrics`, `format` and `as_`, the did-you-mean of an unknown step or keyword, `step_names`, `metric_key` for the `Run.metrics` of a chain, `stubs` for the `.pyi` entries of `step` and `chain`). The library entry for a caller that is not the command line is `chain::prepare` then `chain::execute`; the Python module spells the argv of its keywords and calls `chain::parse` first. `qc.rs` (`QcArgs`, shared by both verbs; prepare: `SOURCES` maps a rule's metrics class to its collector and what it needs, each `Step` carries the Picard argv, `Invocation` and manifest `StepRecord`, `Unmet` lists classes no collector can write), `engine.rs` (`run`: the pass through `pass::run_isolated`, own reads, files via `report::write_atomic` (a `cleanup::AtomicFile`, so a replaced file keeps its mode), post and report, the 12-line summary; `execute`, the same stages silent, returning an `Outcome` with the verdict, parsed inputs, step records and exit code; `collect_tools`, chosen collectors without manifest or verdict, for Python `collect(metrics=[...])`), `manifest.rs` (`PREFIX.manifest.json`, `Fingerprint` of the BAM and of every further file a step's argv names, `StepRecord::resumes`), `events.rs` (`Reporter`: progress line on a terminal, jsonl events; `print_stdout`, which drops output on a closed pipe; `fatal`, the `bammetrics qc:`/`plan:` error line and its jsonl `error` and `done` events), `plan.rs` (text and jsonl plan). `qc --also FORMAT[,FORMAT]` (`also.rs`: `Also`, `targets`, `texts`; `engine::write_also`) writes `FILE.json`, `.jsonl`, `.tsv` or `.csv` beside every metrics file and `PREFIX.report.md`, `PREFIX.junit.xml`, `PREFIX.verdict_mqc.json`, listed in the manifest under the step `also`; a later run removes the ones the earlier manifest lists and it does not write; a metrics file with headers only (`CollectDuplicateMetrics` on a BAM with no read) gets a sibling with no row. `discover.rs` (metrics files found by their `## METRICS CLASS` block at any depth, grouped into samples by `SAMPLE_RULE`), `report.rs` (verdict, page and index per directory, `write` returning the paths, the one-screen summary), `check.rs` (text, json, jsonl, junit, markdown and multiqc forms, a `--format` list with `-o FILE`, `files_read` for the refusal of an output that is a metrics file or verdict it reads, exit codes 10 and 11 from `EXIT_CODES`), `error.rs` (exit 2 for a usage error, 1 otherwise), `python.rs` (the keywords of the Python `qc`, `check` and `report` from the clap arguments of `QcArgs`, `CheckArgs` and `ReportArgs`, `Verb::parse` through the command's parser, the generated `.pyi` block, which ends with `chain::python::stubs()`, `metric_key` for `Run.metrics`, `further_file`). The binary lives here because it needs verdict and report, which depend on core. `tests/golden.rs` is the golden suite; `tests/grammar.rs` the spelling matrix of every verb against the Picard face; `tests/verbs.rs` runs `report` and `check` on `tests/data/picard` (Picard 3.5.0 output for the fixture BAM); `tests/qc.rs` runs `qc` and `plan` on the fixture BAM (Picard-face bytes, resume, isolation, exit codes); `tests/chain.rs` runs `chain` end to end (chained equals staged on the fixture, corpus t1 and the foundation corpus; a chain without a transform equals `qc`; the plan file equals the command line; names, standard output, `STOP_AFTER` in the middle, a failing tap and a failing transform, every usage error, `fifo-buffer` refused as a step and copying the BAM on a pipe into and out of a chain, the library entry); `tests/formats.rs` runs `convert`, a `--format` list, `qc --also` and `check -o` end to end (a BAM with no read, a cell Picard text cannot hold, a byte order mark, the refusal of an input as output, the mode of a replaced file), and MultiQC on a `qc --also multiqc` directory when `multiqc` is on PATH or `MULTIQC` names it; `tests/budgets.rs` is the `#[ignore]`d budget benchmark of `make budgets` (render time median of 31, page and index bytes, binary growth from the two probe examples of `crates/report`, formats growth from `size_formats_base` and `size_formats` of `crates/formats/examples`, one BAM read for `qc` with the report).
- `crates/verdict` (`bammetrics-verdict`, `docs/verdict.md`): presets of threshold rules evaluated over `MetricsDoc`s, and `verdict.json` (schema `bammetrics.verdict/1`). `preset.rs` (`Preset`, `Rule`, `Bound`, `content_hash`), `verdict.rs` (`evaluate`, `Verdict::to_json` and `from_json`), `table.rs` (`parse_tables` for a preset file: it calls `bammetrics_core::toml::parse_tables`, where the TOML subset reader lives since W04, and names the file in the error), `json.rs` (hand-written JSON value, writer and reader). The four shipped presets are `presets/*.toml`, compiled in; every one says `note = "starting values"` (the clinical-panel review is open). `tests/doc_presets.rs` fails when the preset tables of docs/verdict.md differ from the compiled presets. Rules from docs/05 section 4.9: the crate reads the metrics files it is given and nothing else (no other run directory, no history, no user identity, no network, no comment field). No new dependency.
- `crates/report` (`bammetrics-report`): the per-sample HTML page of docs/05 section 4 from a `Verdict` plus the `Input`s it was evaluated over. `page.rs` (`Options { all_plots, date }`, `render`, `write`; the page top to bottom; `fragment`, the body in `<div class="bm">` for the Python notebook view, series and histogram tables cut to 200 points), `plots.rs` (`Family`, `figure`, `figure_with` a point limit: coverage, insert-size, gc-bias, cycle-quality as inline SVG), `svg.rs` (`Chart`, `Scale`: frame, nice ticks, guides, legend, text alternative), `html.rs` (`escape`, `thousands`, `number`), `theme.rs` (palette tokens read back from `report.css` for light, dark and print, WCAG contrast over `TEXT_ON_BACKGROUND`, a test that every text color and background of the CSS is in a pair, `scoped_css`), `report.css` (about 8 KB, inlined; `@media print` puts the light palette back), `index.rs` (`SampleSummary`, `render_index`, `write_index`: the run index of docs/05 section 4.5, one row per sample worst first, one cell per rule). A plot appears only under a warn or fail check whose rule names it, or everywhere with `all_plots`. The caller passes the date, so the same inputs give the same bytes. Snapshots of the fixture pages and the index live in `tests/report/` (`UPDATE_REPORT=1 cargo test -p bammetrics-report` rewrites them; they embed the tool version, so a version bump rewrites them too); `cargo run -p bammetrics-report --example fixture_pages -- DIR` writes the sample pages for a browser, and `bammetrics report DIR` writes everything. Accessibility (0.16.0, axe-core clean): header and footer outside `<main>`, `h1` to `h3` in order, `scope` on every header cell, each table region focusable with `aria-label` (`table_region`), glyphs `aria-hidden` beside a status word, an `.sr` status word in index cells with the glyph drawn by `report.css` (`td.cell.<status> { --glyph }`, empty alternative text; a unit test ties it to `status_glyph`), `.tbl` positioned so the `.sr` words stay inside its scroll box. `make a11y` (`benches/a11y.mjs`, node and npm, not in CI) runs axe-core, the 320 and 360 px reflow with every `<details>` open, and the Tab order on the index and sample pages; the plot shading class is `zone`, never `band` (the verdict banner). `examples/size_base.rs` and `size_report.rs` are the binary-growth probes. Same rules as the verdict crate: inputs only (one exception, the gaps BED beside a `CoverageGapMetrics` file, docs/05 4.9), no script, no network, no dependency beyond core and verdict.
- `crates/formats` (`bammetrics-formats`, docs/formats.md, docs/07 section 3): every output format of a metrics file, from one typed table. `table.rs` (`Ty` `Int`, `Float`, `Str`; `Table { class, columns: Vec<(name, Ty)>, rows }` with each column's type from `glossary::lookup`, inferred only where the glossary has no row, a cell that does not fit widening its column; `Document`: `headers`, the class `tables`, the `histogram` as a second table, `verbatim` for a file that is no metrics file; `Document::from_output` for a tool's `MetricsOutput`; `Table::keys`, one key per column with `.1`, `.2` after a repeated name), `picard.rs` (Picard text read and written through the core's `TextDoc`, a `Double` histogram key as `Double.toString`; `write` is an error for a cell, column name or class with a tab or a line end, which only a JSON document can hold; `read_or_empty` for a file with headers only), `metrics_json.rs` (schema `bammetrics.metrics/1`, `docs/schema/metrics-1.json`: `columns` (the row members, from `Table::keys`), `picard_columns` when a name repeats, `types`, `metrics`, `non_finite` for the NaN and infinite cells JSON holds as `null`; the reader), `json.rs` (hand-written JSON value whose numbers keep their text, depth limit 64), `delimited.rs` (TSV with tab, newline and backslash escaped, RFC 4180 CSV with full doubles, JSON Lines with `"histogram": true` on histogram rows, the aligned `human` text), `markdown.rs` (GFM, the verdict first, a wide short table on its side, cut at 65,536 characters), `junit.rs` (a testsuite per sample, a testcase per rule), `multiqc.rs` (`PREFIX.verdict_mqc.json`), `verdict.rs` (`VerdictSummary`, `CheckLine`: the crate depends on the core only, so `crates/cli/src/format.rs` copies these out of a `Verdict`), `lib.rs` (`Format`, `parse_list`, `render`, `is_json`, `read`, which drops a byte order mark). `tests/round_trip.rs`: Picard text to JSON to Picard text byte for byte on every file of `tests/data/picard` and every metrics file in `tests/golden`, with no member repeated in a JSON object; `tests/schema.rs` validates the writer's JSON under the committed schema; `tests/junit.rs` checks the XML shape and runs `xmllint` when installed. `std` and the core only: Parquet, XLSX and Arrow come behind features (docs/07 W21, W46) and write from the same `Table`.
- `vendor/noodles-cram`: noodles-cram 0.102.0 through `[patch.crates-io]`, outside the workspace (`exclude`), with one change marked `bammetrics patch` in `src/io/reader/container/slice.rs`: the template length of attached mates as htsjdk's `computeInsertSize` (`vendor/README.md`).
- `crates/py` (`bammetrics` cdylib): PyO3 wrapper over the core, verdict, report and cli crates; docs/python.md is its API. `src/lib.rs`: the typed functions, one generated function per registry tool, `read_metrics`, `read_table` (one table through `crates/formats` as the `Table` of `types.py`: a list per column, the glossary dtypes, `to_pandas` and `to_polars` importing their library on the first call), `evaluate`, `collect` in its 0.12 form and the dispatch to its docs/05 form, `__all__`. `src/verbs.rs`: `qc`, `check`, `report`, `tools`, `presets` and `collect(metrics=[...])` over `bammetrics_cli` (keywords become the command's argv through `bammetrics_cli::python`, the GIL released), the `Run` (generic in the stub: `Run[Verdict]` from qc, `Run[None]` from collect and chain; `stages` is one `Stage` per step of a chain run, else empty), `Verdict` and `Check` classes, each with `__reduce__` so it pickles. `src/chain.rs` (docs/python.md, W04): `chain(source, steps, ...)` and `step(verb, **options)` over `bammetrics_cli::chain` (`value_text` and `keyword_args` turn a keyword into `--long=VALUE` with the type checked, a NaN or infinite float and a list of texts with an item that is not a str refused; `argv` adds `+ VERB ...` per step; `run` is `parse`, `prepare`, then `plan_text` or `execute`, without the GIL; `finished` reads every metrics file back), the `Step` class (checked when made, `verb`, `role`, `options`, `args`, equal by verb and args) and the `Stage` class (`status`, `files`, a transform's `records_in`, `records_out`, `changed`). `src/types.py`, run at import: `BammetricsError`, `UsageError(ValueError)`, `InputError(OSError)`, `VerdictError`, the `Tool` and `PresetInfo` str subclasses, and `Table`. `bammetrics.pyi` has two generated blocks (registry tools from core, verbs from cli; `UPDATE_PYI=1 cargo test -p bammetrics-core python_stubs` and `-p bammetrics-cli python_stubs`); its typing-only names start with `_`, so `tests/python/test_mirror.py` can match it with `dir(bammetrics)` both ways. The class entries and the `collect` overloads are written by hand; `tests/python/stub_types.py` holds the call forms `mypy` checks in `make wheel-check`. `tests/python/test_chain.py` runs `chain` and `step` on the fixture BAMs (chained equals staged, each plan file against its inline steps, the command's bytes, stages, metric keys, one error per misuse, pickling, the GIL). `pyproject.toml` points maturin at `crates/py/Cargo.toml`.
- `tools/`: scripts for a builder, not shipped. `spec_agent.py` prints the option table of a Picard tool's `--help` as a starting spec.
- `tests/harness`: pytest tests of the concordance harness itself (the Picard queue, `compare_bam`, `compare_vcf`, `spec_agent.py`) on stand-in tools; `make harness-test`.
- `deny.toml`: the cargo-deny configuration of `make deny` (licences, bans, sources, advisories).

Shared building blocks in `crates/core/src`:

| File | Role |
|---|---|
| `metric.rs` | `Value`, `MetricRow` trait (class, columns in Picard order, one `Value` per column), `MetricsOutput` (`from_rows`, or `histogram_only` for a file without a metrics class), `HistogramSection` with its `KeyClass` (`Integer`, `Byte`, `Double`), `ToolOutput` (the `OUTPUT` file plus extra files with their paths). One writer and one Python converter serve every registered tool. |
| `metrics_file.rs` | Picard metrics text format and `format_double` (htsjdk `FormatUtil`), plus the reader: `MetricsDoc::read` or `parse` gives the header texts, every `## METRICS CLASS` block (`ClassBlock`: columns by name, `get(row, column)`, `find(column, text)`) and the `## HISTOGRAM` section (`HistogramBlock`, `series(label)`), cells typed from their text by `parse_value` (`Value::Int`, `Float`, `Str`, `Null`; `?` is NaN, `0,5` is 0.5). Python `read_metrics(path)` wraps it. `TextDoc` is the same file with every cell as text: `MetricsDoc::parse` types it, and its `write` shares the line writers of `MetricsFile::write`, so `crates/formats` writes a file back byte for byte. |
| `glossary.rs` | `crates/core/glossary.tsv` compiled in: one row per column the tools write (Picard class, column, type, definition in our own words; histogram columns under the program name). `lookup(class, column)`; a test fails when a tool emits a column without a row. |
| `registry.rs` | `Tool` (`name`, `summary`, `options`, `run`, and `collector` for one-pass tools), `Opt` (the option table row: `bool`, `int`, `float`, `text`, `path` with help text, `.repeated()`, `.required()`; `output`, `ignored`, `ignored_bool`, `rejected`), `Invocation`, `TOOLS`, `python_stubs` (the generated block of `bammetrics.pyi`), `python_keywords(tool)` (the keyword arguments of a tool's Python function, which the stub prints and the Python `step` checks against). Parses `KEY=VALUE` and `--KEY VALUE` arguments (a value or output option without `.repeated()` given twice is a usage error, as in Picard), runs the tool, writes every file. `Invocation::single_pass` reads the BAM with `STOP_AFTER` and `ASSUME_SORTED` applied; `run_collector` is the `run` of a one-pass tool. |
| `levels.rs` | `METRIC_ACCUMULATION_LEVEL`: `Level`, `parse_levels`, `Levels<T>` keyed accumulator, read-group lookup. |
| `filters.rs` | `RecordFilter`: unmapped, secondary, supplementary, duplicate, QC fail, minimum MAPQ. |
| `blocks.rs` | `alignment_blocks` from the CIGAR (docs/01 section 2.5) and `alignment_end`. |

## How to add a Picard tool (registry route)

Touch exactly these places. `CollectX` is the Picard class name.

1. New file `crates/core/src/collect_x.rs`:
   ```rust
   pub struct Row { /* typed fields */ }
   impl MetricRow for Row {
       const CLASS: &'static str = "picard.analysis.XMetrics";
       const COLUMNS: &'static [&'static str] = &["A", "B", "SAMPLE", "LIBRARY", "READ_GROUP"];
       fn values(&self) -> Vec<Value> { vec![self.a.into(), self.b.into(), /* ... */] }
   }
   pub struct CollectX { /* Levels<State> or plain state */ }
   impl Accumulator for CollectX {
       type Output = Vec<Row>;
       fn accept(&mut self, record: &bam::Record) -> Result<()> { /* filter, then levels.route(record, |unit| ...) */ }
       fn finish(self) -> Result<Vec<Row>> { /* iterate levels.into_buckets() in order */ }
   }
   pub const TOOL: Tool = Tool {
       name: "CollectX",
       summary: "one row per ...; what the tool returns, for --help, `tools` and the Python docstring.",
       options: &[
           Opt::float(&["LONG_NAME", "S"], "What it does (default 0.05)."),  // also bool, int, text, path
           Opt::text(&["LIST_OPTION"], "Each adds to the default, null clears.").repeated(),
           Opt::path(&["BAITS_FILE"], "The bait intervals.").required(),
           crate::registry::LEVEL_OPTION,                    // METRIC_ACCUMULATION_LEVEL
           crate::registry::STOP_AFTER_OPTION,               // STOP_AFTER; single_pass applies it
           Opt::ignored(&["HISTOGRAM_FILE", "H"], "no plot is drawn"),
       ],
       run: run_tool,
       collector: Some(collector),                           // None for a tool that is not one pass
   };
   fn run_tool(inv: &Invocation) -> Result<ToolOutput> {
       inv.run_collector(collector)                          // STOP_AFTER, ASSUME_SORTED
   }
   fn collector(inv: &Invocation, header: &sam::Header) -> Result<Box<dyn Collector>> {
       let opts = Options::from_invocation(inv)?;            // inv.get / all / parse / parse_opt / flag
       Ok(pass::boxed(CollectX::new(&opts, header), |rows| {
           Ok(MetricsOutput::from_rows(&rows, histogram_or_none).into())   // ToolOutput::NONE = Picard writes no file
       }))
   }
   ```
   Each row is the only place the option is named: it gives the Picard key, the kebab verb flag (`--long-name`, `-S`), the `--help` line, the Python keyword (`long_name`) and its stub type. Every row needs help text and every tool a `summary` (`registry::tests::every_row_has_help_and_one_meaning_per_name`). A Picard boolean that changes nothing is `Opt::ignored_bool`, so the verb reads it as a flag. `COMMON` options (`INPUT`, `OUTPUT`, `ASSUME_SORTED`, `VALIDATION_STRINGENCY`, `TMP_DIR`, `QUIET`, `VERBOSITY`, `R` ignored, ...) need no entry. A tool whose file option is not `OUTPUT` declares `Opt::output(&["METRICS_FILE", "M"])`, and then `O=` is an error; one Picard rejects a common option for declares `Opt::rejected`. A further file goes in `ToolOutput::extra` with its path (`gc_bias.rs`). Any option Picard has that changes the numbers and is not implemented must stay absent: an unknown option is an error. With `collector` set, `CollectMultipleMetrics` can run the tool: add it to `PROGRAMS` in `multiple_metrics.rs` with its Picard extension.
2. `crates/core/src/lib.rs`: add `pub mod collect_x;`.
3. `crates/core/src/registry.rs`: add `&crate::collect_x::TOOL,` to `TOOLS`. Then `crates/cli/src/verbs.rs`: add `verb("x", "CollectX", Files::Single)` to `VERBS` (the name is the class without `Collect` and `Metrics` in kebab case; `Files::Prefix` for a tool that writes several files, `with_input(..., "VCF")` for a tool whose input is not a BAM). `verbs::tests::verb_names_follow_the_table_then_the_rule` fails until it is there. The verb's flags, `--help`, completions and `bammetrics tools` line come from the option table with no further edit.
4. `bammetrics.pyi`: run `UPDATE_PYI=1 cargo test -p bammetrics-core python_stubs`, which rewrites the generated registry block from the option table (the Python function name is the Picard name in snake case; it is created from the registry at import). `registry::tests::python_stubs` fails while the stub and the table disagree, and `tests/python/test_api.py::test_stub_functions_exist` checks the module.
5. Concordance test in `tests/concordance/test_collect_x.py`:
   ```python
   from compare import compare_metrics
   def test_collect_x(corpus, tmp_path):
       compare_metrics("CollectX", corpus / "corpus.bam", ["R=" + str(corpus / "ref.fa")], workdir=tmp_path)
   ```
   The `corpus` fixture (session scope, generated once into `tests/corpus/out/foundation`) lives in `tests/concordance/conftest.py`. `compare_metrics(tool, bam, picard_args, bam_args=None, workdir=None, expect_file=False, seen=None, output_key="O")` runs Picard and `target/release/bammetrics` with `I=` and `O=` (or `output_key`) plus the arguments, then asserts class, columns, row count and every cell string equal, the same for the histogram section, and the whole file after the `StringHeader` lines equal byte for byte. It reports each differing column with the row index and key columns. `compare_outputs(tool, bam, picard_args, outputs=(("O", ""),))` does the same for every file a multi-file tool writes under one directory (`CollectGcBiasMetrics` with `S=`, `CollectMultipleMetrics` with `O=` as a prefix).

The Picard face (`bammetrics CollectX I=... O=...`), the verb (`bammetrics x in.bam -o out.txt`) and the Python function need no further edits.

`crates/cli/tests/registration.rs` is the registration rule: it fails while a tool in `TOOLS` lacks a verb, an argument list in `crates/core/tests/glossary.rs` (or a line in its `EXEMPT` table; the test parses the keys of `args()` and the `EXEMPT` tools, so a name in a comment does not count), a concordance module that names it (`tests/concordance/test_<verb>.py` or `test_<picard_name_in_snake_case>.py`, else a line in that file's `CONCORDANCE` or `NO_PICARD_ORACLE` table), its name in `docs/cli.md`, or a README table row that starts with its name. One failure lists every gap. Start a new tool from `python3 tools/spec_agent.py CollectX` (its `--help` option table). A tool that writes reads uses `compare_bam` in place of `compare_metrics`, a tool that writes a VCF `compare_vcf` (tier B, below).

## Concordance rules

`docs/01_v0.1_implementation_guide.md` is the algorithm spec; section 7 lists the concordance traps. The ones that bite:

- Insert size mean and SD use the histogram trimmed to `median + deviations * MAD` (or `HISTOGRAM_WIDTH`, raised to `MIN_HISTOGRAM_WIDTH`). Every other field uses the full histogram.
- MAD keys the deviation histogram at 2x and halves the result, so half-integer medians stay exact. SD uses `n - 1`. Mode ties go to the lowest key. `min`/`max` are keys, not counts.
- Only second-of-pair reads are counted, so each template counts once. Orientation takes the mate end from `MC`, and from `start + TLEN - 1` without it.

Picard output facts found by running 3.5.0 (full list in the module docs of `levels.rs` and `metric.rs`):

- Doubles print with at most 6 fraction digits, no trailing zeros, `HALF_DOWN` on an exact binary tie (123/128 prints `0.960937`); NaN and infinity print `?`. Integers print as decimals, booleans as `Y`/`N`, null and empty string as an empty field.
- `METRIC_ACCUMULATION_LEVEL` is a list option whose default `ALL_READS` stays unless `null` is given first. Rows come out `ALL_READS`, `SAMPLE`, `LIBRARY`, `READ_GROUP`, each level in `@RG` header order, `unknown` last and only when a record needed it. `READ_GROUP` rows carry the `PU`, not the `ID`. The first `@RG` line lacking the level's field makes an empty unit at its header position; alignment summary prints it as an all-zero `UNPAIRED` row.
- Picard writes no insert size file when every orientation falls under `MINIMUM_PCT`; bammetrics writes none either.
- `CollectGcBiasMetrics` prints the level as `All Reads`, `Sample`, `Library` or `Read Group` with only that level's column set; rows exist only for units with an aligned read. `EstimateLibraryComplexity` writes its library rows in Java `HashMap` order (`java.rs`) and assigns a library only to pairs whose read name parses into tile, x and y.
- `CollectWgsMetrics` `STOP_AFTER` counts emitted non-N loci, and the `PCT_EXC_*` fractions of such a run depend on how many records htsjdk had pulled through the counting filters by then: a pending locus leaves the accumulator only when a record starting two or more bases later is read, and the filtering iterator has always read one passing record ahead. `locus.rs` reproduces both. The fast algorithm (`USE_FAST_ALGORITHM=true`) places a block's events by their offset from the read start but indexes from the accumulator front, so a front one base before the read start shifts them one locus early; `locus.rs` keeps that arithmetic.
- `CollectWgsMetrics` on a reference with a `.fai` but no `.dict` runs; Picard needs the `.dict`. `INTERVALS` takes a BED as well (converted as `BedToIntervalList` would); Picard rejects it.
- `CollectWgsMetricsWithNonZeroCoverage USE_FAST_ALGORITHM=true` is an error in Picard 3.5.0 at the first non-N locus with an alignment event (its collector casts the edge iterator's events to `SamLocusIterator.RecordAndOffset`); `NonZeroFastSink` in `wgs_metrics.rs` fails there too and completes only when no record reaches a locus.
- `CollectHsMetrics` and `CollectTargetedPcrMetrics` share their four histograms between units (`TargetMetricsCollector` fields), so with more than one unit Picard 3.5.0 completes only when every unit before the last has no base counted under the cap; otherwise it throws `numbers of bases in the base quality histogram and the coverage histogram are not equal`. The covered unit's median, 20th percentile and sensitivity include the zero-depth bins the empty units added, and the histogram columns repeat once per unit. `NEAR_DISTANCE` may be negative; `COVERAGE_CAP` below 0 fails the same check. `PER_TARGET_COVERAGE` needs `ALL_READS` alone and a reference.
- `CollectRnaSeqMetrics` counts `PF_BASES` for every non-secondary record (unmapped and supplementary included), classifies every aligned base of every mapped primary record (duplicates and MAPQ 0 included), and counts strand and template columns only for a non-supplementary record with a coding or UTR base over exactly one gene. The rRNA test takes the longest single interval overlap over the fragment (`|TLEN|` from the lower start, the alignment for an unpaired read) and a ribosomal record counts nowhere else. Transcript coverage skips the last base of every alignment block (`addCoverageCounts` runs to the block end exclusive). The best transcript per gene breaks mean ties by `HashMap` order of transcript names, and the histogram sums its transcripts in the `HashMap` order of `Transcript.hashCode`; `ref_flat.rs` and `rna_seq_metrics.rs` keep both through `java.rs`. `RRNA_FRAGMENT_PERCENTAGE=0` without `RIBOSOMAL_INTERVALS` is a validation error; a negative value without them is a `NullPointerException` in Picard and an error here.

- CRAM: htsjdk decodes with upper-case reference bases and checks each slice's MD5 when it needs bases; without `R=` it fails at the first such slice, not at open. Picard 3.5.0 opens a `.crai` beside the CRAM and fails on some (`Attempt to create a bai entry for an unmapped slice`), so the real-data check gives Picard an APFS clone without the `.crai`; bammetrics never opens one.
- `CollectVariantCallingMetrics` writes its detail rows in `HashMap` order of the sample names, divides `PCT_DBSNP` and `PCT_DBSNP_INDELS` in `float`, counts a filtered record only in `FILTERED_SNPS` or `FILTERED_INDELS`, counts `NUM_SINGLETONS` for any variant type (MNP and mixed included) and needs an indexed `INPUT` (bammetrics reads it whole). `GenotypeConcordance` cuts each record to the chosen sample first (a `0/0` or `./.` becomes `NO_VARIATION`, a `./1` stays a SNP), so 11 scheme cells outside the `NA` entries can never be counted (`variant_vcfs.py::UNREACHABLE`); `HET_SPECIFICITY` and `HOMVAR_SPECIFICITY` are always `?`. `AccumulateVariantCallingMetrics` inverts the printed ratios back into counts and is lossy where a ratio printed `0` or `?`.
